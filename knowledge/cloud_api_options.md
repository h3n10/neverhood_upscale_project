# Cloud generative image APIs for project assets

## 2026-10-24 - T8: capabilities, cost, rights, privacy and recommendation

### Decision summary
**Do not upload any asset or API key. No cloud test was run.** This research only used vendor docs/pricing pages, not project content. Before any transmission the project owner must explicitly approve a named provider/model, precise sample files, region, account tier, data-retention/processing terms and IP-rights basis. The source contains commercial game art; provider API ownership language does not establish our right to disclose the assets, nor give clearance to distribute generated derivatives. Ask legal/rights-holder counsel or the owner before sharing or publishing. Never use a consumer/free tier for confidential/copyrighted files without explicit permission and terms review.

**Recommendation:** keep all bulk images/video local. Classical Lanczos/nearest and, only after controlled tests, local Real-ESRGAN are reproducible and avoid third-party transfer. Generative editing is not strict super-resolution: it can redraw shapes, alter palette/light/texture, add/remove details and vary every call. Only consider an opt-in, small, rights-cleared still-image study (a few approved hero assets), as a proposal/reference only, not as the production replacement. Do not use generative image APIs per animation frame.

For 1,000-5,000 stills add $34-$168 at Nano Banana 2.1 1K, $113-$565 at 4K, or $2-$10 for listed Real-ESRGAN. If every frame gets two attempts, roughly double output costs; a retry loop of 3 increases that line by ~3x. Current Google Batch pricing lists ~50% image-output reduction for eligible models, but this does not change the core rights/privacy/artifact risks or batch duration. Actual archive frame total must be read from manifest before any estimate is treated as a budget. API rate limits also mean hundreds of thousands of calls may take days/weeks without quota increases; model calls/outputs can be variable. Use the scale scenarios, not a promise of throughput.

### Risks and safeguards
- **Content/style drift:** prompt-based editing is a semantic generation task, not deterministic interpolation. Can add wrinkles/highlights, change clay silhouette, facial expression, object count, framing, lighting or palette. Stronger prompt constraints are not a guarantee. A visually attractive image can still be a wrong asset.
- **Temporal inconsistency:** per-frame calls independently redraw details; character/reference-image features and multi-turn editing do not guarantee matching pixels across hundreds of frames. Frame drift/flicker can appear even when each still looks plausible. Never use a generic diffusion/generative API as an animation-wide upscaler.
- **Rights:** source archive art is likely third-party copyrighted material. Check project permission, provider terms, jurisdiction, derivative-use/distribution rights, sublicensing, opt-outs, provenance and asset-owner approval. Provider output-ownership terms do not clear underlying input rights or third-party claims. Do not publish commercial derivatives without permission.
- **Privacy/security:** an image upload is an external disclosure. Review DPA, retention/deletion, subprocessors, training/review use, region, access controls, logging/webhooks and backups. Google's unpaid Gemini terms explicitly allow submitted content and generated responses to be used to improve/develop products and may be human reviewed; paid tier is listed as not used for product improvement, but still review API terms. OpenAI API default abuse logs up to 30 days; approval-based retention controls exist. Replicate API data defaults to one-hour cleanup per docs; verify actual account and saved outputs. Use no API keys in scripts; if approved, secrets vault/env injected, least privilege, spend caps, no keys in logs.
- **Local alternatives:** FFmpeg/Pillow classical scaling is already installed and reproducible, no upload, no per-frame fee. Local Real-ESRGAN can be installed only after size/dependency review; it is learned and can hallucinate but keeps images on-machine and pinned weights/configs permit repeatable batch processing. Existing Intel UHD 620/Python setup lacks PyTorch; cloud is not automatically safer or more suitable. Research local-vs-cloud artifact behavior on authorized non-sensitive sample/copy first.

### Proposed hybrid, gated
1. Classify and hash every asset. Local deterministic baseline for all bulk frames/stills; preserve source SMK/indexed palette and timings.
2. Tier C bulk: only classical scaler or separately approved local learned model. No cloud-generative calls. Automated checks on every output and stratified manual sampling (QA policy in `knowledge/qa_process.md`).
3. Tier B important backgrounds/animation keyframes: compare local methods; no frame-only cloud edit unless all paired neighboring frames are subsequently checked.
4. Tier A hero stills/backgrounds: after rights + privacy approvals and user approval of a pilot style, optionally submit a handful of stills to a named generator. Keep unchanged source and local baseline; output is a *candidate study*. A human can derive a style/texture constraint guide from approved source references; do not let that guide authorize new scene content. VLM reviewer is advisory and separate third-party data transfer.
5. Never promote a cloud result from pilot to production automatically. Obtain explicit user signoff of method, visual deviations, release rights, privacy terms, budget and human QA staffing. No asset was sent in T8; no key was requested or used.
